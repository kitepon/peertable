### 2.2 配置表の見直し

現行表の「実装物量 = Terra×medium」「Luna×low = 分類・抽出」「max は既定禁止」だけでは、値下げ後の性能単価を表せない。

計画候補:

- `Luna×low`: 分類・抽出・定型変換。
- **`Luna×max`: 仕様が固まり、focused test で成否を判定できる小規模・限定的な実装、テスト作成、修正。**
- `Terra×medium`: 探索・判断・広い文脈を含む通常実装。
- `Sol`: 設計、不確実性の解消、敵対的検証、契約クリティカルな判断。

OpenAI は、Sol が不確実性を解消して計画し、Luna が well-specified changes の実装・テスト・評価を担う構成を公式例として挙げている。GPT-5.6 公開評価でも Luna は coding agent 指標で旧来の軽量分類専用という位置づけを超える性能を示している。

ただし、ベンチマーク値だけで既定を確定しない。代表的な仕様確定済み小規模修正を `Luna×max` と `Terra×medium` で同条件実測し、成功率・手戻り・総消費量・完了までの反復を比較してから配置正本を確定する。機械的なファイル数閾値は作らず、判断語彙と適用例を正本化する。

## 3. 席設定変更の柔軟化

### 3.1 現在の欠陥

`skill/scripts/change-effort.sh` は、本人から親への DM body が `[effort変更依頼] <level>` と完全一致することを要求する。自然文の中で意図が明確でも拒否し、親が「その1行だけ再送せよ」と要求する運用になった。

これは Peertable の過剰設計禁止と、AI が意味を判断できる領域を機械形式へ過剰に押し込めない方針に反する。本人の意図が明確なのに exact body を要求する仕組みは廃止する。

### 3.2 目標

- effort だけでなく **model も変更可能**にする。
- model-only / effort-only / model+effort の一括変更を扱う。
- 親が自然言語の依頼を意味解釈し、明示的な imperative script を実行する。script が room の文章を再解釈・完全一致確認しない。
- model-only は effort を、effort-only は model を保持する。
- model と effort の組合せを live catalog / vendor 境界で検証する。
- 同値変更は再起動しない。
- 席の再起動は context を失うため、再着任経路を維持する。
- busy 保護と、外部再起動失敗時の明示 rollback は残す。どちらも外部境界の実在リスクであり、exact DM 検査とは性質が違う。
- 失敗を別モデル・別 effort へ黙って fallback しない。

実装形（新しい汎用 script 名と既存 `change-effort.sh` の互換 wrapper を残すか）は未決。npm 配布面との互換性と過剰装備禁止を同時に満たす最小形を工程で決める。

## 4. メンバーの自律性と進捗の流れ

### 4.1 観測された問題

親が「円卓に必要なこと以外回答するな」「指示に従え」等を強く言うと、メンバーが自律的な進捗報告まで抑制し、報告なしで turn を終え、無駄な空白が生じることがある。

一方、共通 room へ進捗報告が流れていた時期は、メンバーがより自律的に動いていた。候補原因は次の二つであり、混同せず実測する。

1. メッセージ注入が idle 席の turn を起こしていた。
2. 可視化された行動が「進めて報告するのが正しい」という相互規範を強化していた。

### 4.2 入れる規律

- 親の局所的な簡潔化・従属要求は、Peertable の自律作業ループと必要な報告義務を停止させない。
- 仕事を持つ席は、進捗・完了・blocker・明示的待機のいずれかを記録して turn を閉じる。
- 停止できるのは、オーナーによる明示 pause、承認待ち、外部依存待ち、または安全に進められない実在 blocker の時だけ。
- 親から新しい指示が来るまで待つことを通常状態にしない。
- 報告の可視性と、誰の turn を起こすかを分離する。全員 broadcast の復活を先に決めず、roomログの可視性・pull・対象限定 wake の組合せを比較する。
- 進捗報告が自律性を上げる効果と、不要な注入による token / turn 増加を実運用 smoke で測る。

### 4.3 空いている工程を自分で探して着手する義務

円卓のメンバーは、親からの割当や許可を待たず、着手可能で未担当の工程を自分で探して claim / start する。これは推奨ではなく、円卓へ着任したメンバーの作業義務とする。

現行実装でも、次の指示によってこの pull 型の行動は既に強く誘導されており、実運用でメンバーが自発的に工程を拾っていたのは偶然ではない。

- 着任指示: 「作業ループを開始せよ。全タスク完了の宣言まで自律的に続けること」 (`skill/SKILL.md`)
- member role: 「作業を選ぶのも始めるのもあなたである」 (`skill/templates/member.md`)
- charter: task 完了後に工程正本を再確認し、残っていれば claim へ戻る (`skill/templates/charter.md`)
- Lattice は仕事を配らず、席が自分で `todo start` する pull 型である。

不足しているのは、`ready があるのに待機してはならない`という義務と探索順序の集約である。改修後は、着任時・再着任時・自分の工程完了時・blocker 解消時に工程正本を確認し、次の順で動く。

1. 自分が既に持つ active 工程があれば、それを完了させる。
2. claim 範囲内に未担当の ready 工程があれば、自分で適切なものを選び、room へ claim を出して start する。
3. ready が無ければ、文脈近接かつ未担当の peer audit 対象を探す。
4. 実装・監査とも着手可能なものが無い時だけ、待機を記録する。

「積極的」は無意味な連続 polling や仕事の発明を意味しない。claim 済み工程の横取り、phase / campaign の越境、同一席による複数 WIP、受入条件外の自主改造は引き続き禁止する。親は工程を配車せず、メンバーがこの優先順を自律的に実行する。

現行 `member.md` には「ready が無ければ done を監査する」と「依頼されていない監査へ自発参加しない」が併存している。相互監査の復活と合わせ、工程正本上で監査対象と担当有無を判別できる形に揃え、メンバーが親の指名を待たずに監査へ移れる契約へ解消する。

## 5. 親の役割境界

### 5.1 親が既定で持たないもの

- 工程内の技術監査。
- Lattice の task 起票、start、note、done 等の工程管理操作。
- メンバー間合意の再掲、次作業の指名、工程の代行。
- 不足した peer audit や工程記録を親が埋めること。

Peertable を使う時点で、この親向け規律が Claude 親・Codex 親の双方へ確実に入力される仕組みを持たせる。親が読めば守れるという期待だけでなく、setup / 再着卓時の正規 role 文書に置く。

### 5.2 親が行う完成確認

重要な順序は **全工程完了後ではなく、各工程完了後**。

1. 担当メンバーが工程の成果を実装・検証する。
2. 文脈の近い別メンバーが peer audit を行う。
3. 必要な修正を反映し、工程記録と Lattice 完了を登録する。
4. **その後で初めて**親が、元の設計思想・工程記録・その工程の完成部分を黙って照合する。
5. 問題なしなら受理する。
6. 問題があれば、その工程へ差し戻す。親は修正・task化・工程管理を代行しない。

親はこの照合を「メンバーに言わずに」行う。事前にレビュー依頼や相談を求めず、工程登録前にチェックしない。完了前に親が確認すると、メンバーが親の監査を期待して自らの相互監査と完成責任を手放すためである。

親の黙った完成確認は peer audit の代替ではない。問題がなければメンバーへ追加の指導・総括を流さず、問題がある場合だけ工程を差し戻す。

## 6. 相互監査の復活

親が監査を持たなかった運用では、各工程を担当した記憶や近接文脈を持つメンバー同士が相互に監査していた。親が監査を持つようになるにつれ、この動きが消えた。

復活させる契約:

- 各工程は実装者とは別の一席が監査する。
- 監査者は、同じ工程または隣接工程の記憶を持つ **文脈近接の独立一席**を優先する。
- 監査所見と実測を room / 工程記録へ残す。
- 親は工程内監査者として数えない。
- 親の受理は、peer audit と工程完了登録が揃った後だけ行う。
- 手の空いたメンバーが監査へ回る自律ループを戻す。親が監査者を逐一指名する運用にはしない。

現行正典には決定60・67として卓内監査の骨格がある一方、古い「親の監査」表現や、親の受理と監査を混同させる記述も残る。実装時は新規則の追加だけでなく、矛盾する既存記述を解消する。

## 7. Codex 親への対応

円卓の親は Claude 固有の人格・機能ではなく role であり、Codex（この Codex / ベル）でも担える設計にする。

確認が必要な面:

- AGENTS.md / 親 role / Peertable skill の読み込みと再着卓。
- room の読み書き、Lattice の read-only 観測。
- 各工程完了後の黙った完成照合と差し戻し。
- Claude channels / Monitor と異なり、idle な Codex 親を room message が自動で起こせるか。
- 自動 wake が無い場合の正規 connector。手動監視を成功扱いする fallback は作らない。

Claude 親と Codex 親の両方で onboarding・進捗・peer audit・工程完了後確認を smoke し、provider-neutral な契約として受け入れる。

## 8. 現時点の受入像

- 自然文で明確な席設定変更を、exact DM の再送なしで親が実行できる。
- model と effort を独立または同時に変更でき、再起動後 metadata と履歴が一致する。
- 親の抑制的な発言後も、作業中メンバーが必要な進捗を残して自律継続する。
- 未担当の ready 工程があるのに、親の割当を待って待機しない。
- 工程管理と工程内監査を親が奪わず、担当メンバーと peer が閉じる。
- 各工程の完了登録前に親へレビュー依存しない。
- 各工程の完了登録後、親が黙って設計・記録・完成部分を照合し、問題時だけ差し戻す。
- 文脈近接 peer audit が全工程で実在し、親の完成確認で代用されない。
- Claude 親・Codex 親の双方で同じ役割境界が成立する。
- dotagents の最新モデル配置を使って円卓の model / effort を選べる。
