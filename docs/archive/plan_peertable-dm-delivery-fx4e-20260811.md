## 工程

### k1 DMを在席中の宛先へ一度だけ届け、turn開始と既読まで保証する

- [x] k1の実装・試験・証跡化を完了した。後続の現行実装方針を正とする。

2026-08-11 の実円卓で、room API の DM 自体は保存される一方、Peertable repo の
`.team/wakeup-bridge.json` は初期席 `tsubaki` だけを監視し、後から追加した `kanade`、`nagi`、
`asahi` を追従していなかった。Lattice repo には wakeup bridge の状態ファイル自体がなく、room に
送った DM がどの席の turn も起こさなかった。親が外部 PTY へ本文と Enter を手で送ると初めて席が
動いた。room ログへの保存成功を「DM が届いた」と扱っている現在の状態は、円卓の調整路として
致命的な欠陥である。

DM の配達成功を、`roomへ保存済み` ではなく **宛先の在席判定、対象席への一回だけの wake、turn 開始、
room client による未読取得**までの連鎖として扱う。bridge は room の現在メンバー集合と席の生存状態を
自動で追従し、席の追加・設定変更・再起動・退席のたびに監視対象を手作業なしで収束させる。setup 済みの
room に bridge がない、死んでいる、監視集合が古い場合は、親へ自然な次の一手を返すだけで終わらず、
通常運用で安全に再生成・再 arm できる正規入口を用意する。宛先不在、席停止、注入失敗は保存成功へ
丸めず、誰にどこまで届かなかったかを typed に残す。同一 DM の再走や bridge 再起動では二重注入しない。

既に再 open した `peertable-autonomy-runtime-fx-20260811/f2` は、`ensure-bridge.sh` と席集合 reconcile の
直接欠陥を先に直している。本工程はその WIP を奪わず、f2 の成果を入力として **製品全体の配達保証と
実席 E2E** を閉じる。f2 が下記受入を全て満たした場合は重複実装せず、実測・証跡・本開発への deploy で
完了してよい。満たさない差分だけを本工程で直す。

受入は次の通り。

1. room 稼働後に Codex 席を追加しても、設定ファイルの手編集なしでその席が DM の監視対象になる。
2. 席の設定変更・再起動後も同じ member identity へ配達でき、退席後は死んだ PTY を保持・注入しない。
3. bridge 不在・停止・監視集合の陳腐化を検出し、通常運用の正規入口だけで自動復旧できる。
4. 一つの DM は宛先ごとに一回だけ wake され、再起動・再 poll・複数 bridge 競合でも二重注入されない。
5. 保存、wake、turn 開始、未読取得の各段階を区別し、途中失敗を「配達済み」に見せない。
6. 実 Codex 席を追加した room と別 repo の room の双方で、DM送信→turn開始→`read_unread` 取得を実測する。
7. 修理を本開発へ deploy し、その後の実円卓で親の手動 PTY 注入なしに DM が届くことを確認する。

通常 message の broadcast は復活させない。工程着手・工程終了の全体通知は別工程の専用 event とし、
本工程は明示された宛先への DM 配達だけを扱う。
